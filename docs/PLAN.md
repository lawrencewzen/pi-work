# Weft · 方案（v0.2）

## 1. 目标
在公司内网 Windows 上，通过浏览器使用一个基于 Pi Durable 的编码 Agent。模型中断、进程崩溃以后，它能自己从检查点恢复并接着推进。界面要简约。

基础：fork xiaomoBoy/pi-durable-assistant（MIT 协议，Node 22，原生 JS + SSE，SQLite）。保留它的 Harness、持久化和恢复机制，前端整体重做。微信通道已移除。

## 2. 功能需求
**左栏**
- 工作区列表，每个工作区对应一个本地目录。
- 当前工作区下的对话历史，支持新建、归档和搜索。
- 每个会话显示一个状态点：运行中 / 等待中 / 恢复中 / 失败 / 完成。

**中栏（对话）**
- 用 Markdown 渲染回复，代码要高亮。
- 工具调用默认折叠成一行，例如 `✎ write  src/…/foo.ts  +12 −3`、`📖 read  docs/…/a.md`。路径过长时省略中间部分，点开能看到详情。
- 顶部状态条显示当前步骤、上次检查点时间、自动续跑次数，并有暂停、继续、停止三个按钮。

**右栏（可收起）**
- 点击改动过的文件，显示 diff，支持并排和行内两种视图。
- 点击普通文件，以只读方式查看内容。
- `.md` 文件用 Markdown 编辑器打开，可以编辑并保存。
- 选型：diff 和代码查看用 CodeMirror 6 的 merge 扩展，Markdown 用 Milkdown（备选 Monaco diff）。

**Durable 能力**
- 检查点持久化。
- 进程重启后自动恢复。
- 模型输出中断、超时或返回空内容时，自动重试并续跑（次数和间隔可配置）。
- 卡住检测，例如 N 分钟没有进展就提示或续跑。

**新增的 Agent 工具**
原项目是个人助手，没有文件和命令工具，所以要补上：
- `read`、`write`、`edit`、`ls`、`grep`、`bash`。
- 这些工具只能在工作区目录内操作。
- 每次写入都要记录 diff。

**风格**
- 中性灰配一个低饱和度的强调色，支持浅色和深色。
- 字体和间距统一，比原版更素。

## 2.5 多 Agent：角色与流水线
- **角色（Role）**：名称 + 系统提示词 + 允许的工具 + 模型（可各自不同）。内置 test-writer / coder / auditor / planner，用户可在界面或 `roles/*.json` 新增。
- **流水线（Pipeline）**：角色串联/并联的固定流程，如 `test-writer → coder → auditor`，可设置失败回退（审计不通过 → 回到 coder，最多 N 轮）。存为 `pipelines/*.json`。
- **并行**：同一工作区可同时跑多个 Agent，每个是一个独立 Durable Task，有自己的会话、检查点和状态；左栏显示状态点，可单独暂停/继续/停止。
- **写冲突**：同一文件同时只允许一个 Agent 写（文件级锁），冲突时排队并在界面提示。

## 3. 架构
- **编排器（Orchestrator）**：调度角色与流水线、并发上限、Agent 间交接产物（测试文件、diff、审计报告）。
- **监控（Monitor）**：心跳 + 进度时间戳，卡住检测、模型中断自动续跑、指数退避重试。
- **后端**：Node 22 + `@earendil-works/pi-durable`（Harness / Task / SQLite），以 npm 库的形式嵌入，不是独立服务。
  - 对外提供 REST + SSE 接口：工作区、会话、消息、工具事件、文件读写、diff、运行控制。
  - 模型统一走 OpenAI 兼容接口（`LLM_API` / `LLM_BASE_URL` / `LLM_MODEL`）。
- **前端**：Vite + 轻量框架（建议 Preact 或 Vue），构建产物放进 `public/`，内网只部署静态文件和 Node 服务。
- **部署**：Windows 上直接用 `node server.mjs` 跑（便携版 Node 22），不依赖 Docker；Linux 上可以用 Docker Compose。

## 4. 分工
| 角色 | 执行者 | 产出 |
|---|---|---|
| 需求/方案、总控、最终验收 | 小劳（Grok Bot） | 本方案、验收截图 |
| UI 设计 | Antigravity CLI（agy，Gemini 3.8 Flash） | 先出静态高保真页面（HTML/CSS）给劳伦斯看 |
| 写代码 | Grok CLI（grok-4.6） | 后端工具与 API、前端实现 |
| 写测试、跑验收用例 | Cursor cloud agent（可以和写代码的是同一个，也可以单独派） | 单元测试（`node:test`）、端到端测试（Playwright） |
| 代码审计 | 独立的审计 Agent | 安全审查（路径穿越、命令注入、鉴权）、恢复逻辑审查、问题清单 |

**流程**
1. 方案定稿。
2. 并行：agy 出设计稿，测试 Agent 根据方案写测试。
3. 写代码的 Agent 实现功能。
4. 测试 Agent 跑测试，不通过就打回重改。
5. 审计 Agent 审查。
6. 小劳亲自验收。

## 5. 测试方案
- **单元测试**：路径省略显示、+N/−M 统计、diff 生成、工作区沙箱（禁止 `../` 越界）、续跑策略、SSE 事件序列化。
- **端到端测试（Playwright）**：
  - 新建工作区和会话，发消息，看到 Markdown 渲染。
  - 工具行折叠、展开，点击文件后右栏出现 diff。
  - 用 Markdown 编辑器保存文件，确认内容落盘。
  - 暂停、继续、停止按钮。
  - 刷新页面后状态不丢。
- **模拟中断**：
  - 用 `faux` 模型和一个"断流"桩：模型中途断开或超时，验证会自动续跑。
  - 任务进行中直接杀掉 Node 进程再重启，验证任务从检查点恢复、没有重复写文件、界面显示"恢复中 → 完成"。
- **真实运行**：接真实模型跑 2–3 个全流程任务，例如"创建小项目、写代码、跑测试、修 bug"，期间人为制造中断，确认能自动推进。

## 7. 风险与未知
- **模型接口**：Pi Durable 需要一个 OpenAI 兼容接口和 API Key。这台机器上的 grok CLI 是用 grok.com 账号登录的，没有 xAI API Key。真实测试有两个选择：申请或提供 `XAI_API_KEY`（api.x.ai，兼容 OpenAI），或者先用机器上已有的 DeepSeek Key。
- **内网条件**：公司内网能访问哪个模型接口、能不能装 Node 22、能不能执行 `bash`（Windows 下要换成 PowerShell 或 cmd 适配），都还没确认。
- **工具补齐**：Pi Durable 本身是否自带编码工具集还要确认，可能需要我们自己写，工作量会增加。
- **恢复语义**：`bash` 和写文件这类有副作用的操作，恢复时要避免重复执行，需要靠幂等设计和检查点粒度来保证。
- **原项目状态**：原项目是作者个人的实验项目（v0.1，依赖 pi-durable 1.1.0，目前最新是 1.2.0），之后合并上游更新可能有冲突。
- **本机环境**：机器上的 Node 是 v20，项目要求 22.13 以上；没有 Docker；Playwright 浏览器也需要安装。
